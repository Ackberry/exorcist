Exorcist.

A lockfile, a candle, and a local model.

Your agent runs npm install and something you have never read starts executing on your machine. Exorcist scans what is already installed, flags the suspects with deterministic rules, then hands each one to a Gemma model running on your own hardware. Nothing leaves the laptop.

The oracle

What Gemma said

Rules decide who is a suspect. Gemma decides what the suspect is doing. Both answers below are real captured responses from gemma3:4b on Ollama 0.40.11, checked into the repository as test fixtures so they can be verified without a live model.

soul-snatcher suspicious score 65 · conf 0.75
“The package runs a postinstall script that reads environment variables and encodes them in base64, despite claiming to be a harmless demo fixture.”

The package description calls itself harmless. The model read the code and did not take its word for it — untrusted text is fenced off in the prompt and cannot talk the verdict down.

lodasg impostor score 42 · conf 0.99
“The description, README, and code all explicitly state that this package is the ‘lodash’ library, despite the installed name being ‘lodasg’.”

Impersonation alone keeps the package at its rule floor of 28 and the fix stays swap. The model can raise a score; it can never talk one down, and it cannot turn a naming problem into a removal.

If Ollama is not running, the scan still finishes and the report is built from the rules alone. The model is a second opinion, not a dependency.

Four rules

The ghosts it knows

Poltergeist
Install hooks, and risky APIs anywhere in the package: child_process, network modules, process.env, SSH paths, .npmrc, eval and Function, base64 blobs, and names hidden behind \xNN escapes.
Doppelganger
Impostors. lodasg pretending to be lodash — one edit, a separator swap, a dropped scope, a .js suffix, a short combosquat affix.
Phantom
A direct dependency the project never imports, requires, or names in a root script. Installed, paid for, never used — and its install hooks still run.
Revenant
A release that landed after a year of silence, or under a maintainer the previous release did not have. The only rule that asks the npm registry anything.

Install

Run it on your own tree

Node 22.13 or newer. The scanner reads package source; it never executes it.

Clone and build

git clone https://github.com/Ackberry/exorcist && cd exorcist && npm ci && npm run build

Scan without a model

Deterministic rules only. No Ollama needed, nothing on the network except the registry lookup revenant makes.

node dist/cli.js /path/to/your/project --no-oracle

Add the oracle

Pull the model once, leave Ollama running, and drop the flag. Gemma reads only the packages a rule already flagged.

ollama pull gemma3:4b && node dist/cli.js /path/to/your/project

Or take the JSON

stdout carries the report and nothing else, so it pipes.

node dist/cli.js . --no-oracle --json | jq '.hauntings[] | {name, hauntingScore, exorcism}'

Expect false positives on a real tree. Scanning this repository's own 346 packages produces 100 flagged, most of them revenant findings at pin. The score is a starting point for a human, not a verdict to automate on.

How it is built

Open pieces, all the way down

Gemma 3 4B, via Ollama
The only model in the project, running locally. It returns structured JSON with a verdict, a confidence, a score and a reason. Package contents are fenced as untrusted data so a malicious README cannot argue its way to a pass.
Mastra
The scan is a workflow of five steps — resolve, rules, prepare, judge, score — and the judge is a Mastra agent over that open model, with structured output and no tools.
Sentry Agent Tracing
Every judge call is a span with its latency and token counts. Opt-in behind SENTRY_DSN, metadata only unless you ask for more.
Why local matters
A package scanner has to read untrusted code. Pipe that to a cloud model and you have built a new injection target and shipped your dependency tree off the machine. Local stays local.
